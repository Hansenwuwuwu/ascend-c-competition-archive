# 题目 05：SwiGLU——前三名实现的设计复盘

> 归档边界：2026-11-08 的公示页快照未附 SwiGLU 获奖源码。2026-11-09 维护者收到用户本地提供的 `1.zip`、`2.zip`、`3.zip`；以下第 1/2/3 名映射沿用用户给定，不声称是公示页附件或独立核验的作者提交。源码文件、Hash、逐文件审计和不确定项见[完整前三名源码审计](05_SwiGLU_TOP3_LOCAL_SUPPLEMENT_20261109.md)。

本复盘的目标不是逐句转录源码，而是说清每份实现的整体路线、值得借鉴的选择，以及借鉴时不能丢掉的数学和调度前提。本次只做静态审阅，没有重新编译或运行三份获奖代码。

## 1. 题目结构与评测边界

输入为 FP16 的 `X[...,d]`、`W1/W2[d,d]` 和 `b1/b2[d]`，输出与 `X` 同形同类型：

```text
z1 = X · W1ᵀ + b1
z2 = X · W2ᵀ + b2
Y  = (z1 / (1 + exp(-z1))) · z2
```

九个固定测试点覆盖三种工作形态：极小 `M` 的小向量、非对齐窄维的小矩阵、以及 `M=512/4096/8192` 的 Cube 主导矩阵。统一使用一个 GEMM 路径会把小任务的启动/搬运成本和大任务的 Cube 吞吐问题混在一起，因此三份实现都按 shape 分流。

本届 CANNJudge 环境记录为 CANN 9.0.0.0、Ascend 910B4、20 AIC。此为比赛环境，不代表 ZIP 中 CMake 已将 SDK patch/build 固定为该版本；源码本身也不能证明它在本地复现。所有名次映射来自用户提供的 ZIP 顺序。

## 2. 三份实现的主路线

| 提供顺序 | 整体思路 | 最值得看的设计 | 主要边界 |
|---|---|---|---|
| 第 1 名 | Host 按 `M,d` 选择 tiny/vector、分组 vector、Cube/Vector 混合等专用家族；Cube 路径以自管数据布局和流水为主。 | 两路投影共享输入；case8 静态掩码与 32+1 尾维；case9 将两路投影打包到 N=256 并用双 GM 槽交接。 | key、模板、Host shape 守卫、workspace 与同步必须配套；不能只搬某个 kernel 片段。 |
| 第 2 名 | 结构较模块化：小 shape 使用 AIV-only，较大 shape 通过 Cube/Vector pipeline，case9 有按资源预算选择的 resident 路径及回退。 | `NegativeSilu` 配对符号变换；Cube 两路投影错开权重装载；resident 计划先核容量再选路。 | 运算次序涉及 FP16 舍入；权重驻留依赖目标芯片实际容量；头文件中的注释草稿不是活跃 key。 |
| 第 3 名 | 模板路径最多，Host 对九种 shape 做精确路由，分别落到 tiny GEMV、packed GEMV 或 Cube/Vector pipeline。 | 非对齐小维专门 packed 布局；不同 tiling key 使用精简的 tiling ABI。 | 大量 PATH 文本并不都可达；同名 PATH 在不同 key 编译区不一定是同一实现；部分低层 wrapper 与编译/运行时绑定。 |

判断“实际设计”时应从 Host 路由开始，依次核对 tiling key、编译区、kernel 入口、设备执行分支和数据布局。仅在源码中找到某个模板或 PATH，不足以证明评测 shape 会运行它。

## 3. 按 shape 看设计亮点

### 3.1 小 shape：先省掉不划算的固定流程

case1/2/4/6 的输出规模很小。三份代码都用 AIV/vector 或标量专路，而不是为了少量乘加启动完整 Cube GEMM 与通用混合核流水。第 1 名还把极小维度做成固定长度的 batched/tiny 路径；第 2 名用静态 key 区分小行宽；第 3 名则为这些维度各分配 AIV-only PATH。

可迁移的不是这些维数常量，而是**用固定 shape 估算 Cube、workspace、同步和 GM 搬运的固定开销，再决定是否改走向量核**。适用判断需按题目实际 shape、dtype、精度契约和设备启动成本重新计算；“小”不是只看 `d`。

### 3.2 case7：权重复用与尾维处理一起设计

`d=13,M=21` 是非对齐窄维。获奖实现采用小行组共享权重，或由 GEMV/向量路径处理，并对 padded lane 使用 mask/有效元素规约；布局和行组大小共同决定权重重复读取、归约工作量与尾部处理。可复用的是**固定窄维时，把 padded layout、有效 lane、行组 owner 和输出压缩合并设计**，而非机械地将 `13` 补到 `16`。

### 3.3 case8：33 维的关键是静态化数据选择，不是单纯减核

第 1 名 Host 对 `M=85,d=33` 命中 `ROWS=8` 的 `FAST33` vector 实例：每块 8 行，launch 16 个 block，其中 11 个 active block 覆盖 `10×8+5=85` 行，5 个填充 block 直接返回，最后一个有效 block 处理 5 行。设备端把 `33` 拆成 `32+1`：常量 bitmask 配合 `GatherMask` 选择主段和尾项，主段做乘积与规约，尾项通过 `MulAddDst` 合入累加，最后将 padded 48 槽结果压回 33 个有效输出。

这里的亮点是**让固定非对齐维度的索引/掩码成为编译期常量，并同时固定行分组、尾组和写回布局**。它并没有消灭所有 gather/pack：仍有 `GatherMask` 与 48→33 的输出整理；可迁移的是设计方法，不是 mask 常数。若只减少核数而保留动态索引和长归约链，未必更快；该结论也与本项目 T208 等历史尝试相符，但这些自身实验不能替代获奖源码的因果证明。

第 2 名走 `ROWS33` AIV-only 分组；第 3 名 PATH50 使用 packed multi-block GEMV。三者共同点是固定布局和分组，具体数据表示并不相同，不能混成一个所谓通用“33维算法”。源码细节见[审计报告第 3 与第 11 节](05_SwiGLU_TOP3_LOCAL_SUPPLEMENT_20261109.md#3-第一名最多层次的-host-调度与-cubevector-组合)。

### 3.4 case3/5/9：两路投影按同一数据流组织

在大 `M` 上，主要工作是两路投影与门控。第 1 名的 Cube 路径将两路权重纳入同一计算计划，重用 `X`，再由 Vector 侧完成 bias、SiLU 和逐元素门控；具体 tiling 依 case 区分：case5 使用双 C0 两波策略，case9 的 full-row 实例把两路投影打包在 N=256 面上。case9 的每条 Mmad 仍按 K=64 子块推进，并不是单条指令完成全部 K=256。GM 输出槽和 CrossCore flag 用来交接正在生产/消费的数据。

第 2 名把 Cube、Vector、resident 与 fallback 分成模块；其优势是数据流边界容易定位，复用前仍需核对 L0/UB/workspace 容量。第 3 名用多个 key-specific pipeline 类处理大 shape，模板数量多但真实路径要按 Host 的 key 和对应编译区确认。

可迁移的原则是**把两次投影视为共享 X 的联合调度问题**：比较复用 X、延迟装入第二路权重、并行窗口、结果写回槽位和消费者等待。每种优化都要先画清楚 producer/consumer、buffer 生命周期及数值落点，再决定能否重叠；仅把两段代码放进一个 kernel 并不自动形成有效流水。

## 4. 可借鉴方法：按证据与适用条件分类

### S：源码确认的实现事实

- 第 1 名 case8 的 Host→`DIM_TAG=14`→`ROWS=8/FAST33` 路由，以及 16 launch、11 active、尾组 5 行，源码可闭环核对。
- 第 1 名 case9 的 `FULL_ROW_TILE` 实例派生 `PACKED_N`、`DOUBLE_GM` 和 `ROW_PREFETCH`；N=256 合并两路，GM 双槽按迭代槽位管理。
- 第 2 名 `NegativeSilu` 的两个负号并非孤立的“负 SiLU”近似，而是与调用端 bias/projection 的 `Sub` 顺序和最终门控乘法配套。
- 第 3 名 Host 对固定 shape 的早期专用路由会先于通用 fallback；其 `return` 之后的路由代码不可达。key-specific 编译区中同名 PATH 不代表执行实现完全相同。

这些是源码中的事实，不代表每条路径都在本地重新编译或独立测过。

### M：可推导的数学/布局关系

第 2 名的变换为：令 `z=projection+b`，调用顺序 `(-b)-projection` 得到 `-z`；`NegativeSilu(-z)=-SiLU(z)`。若另一门控支路也取负，最终乘法中两个负号相消：

```text
(-SiLU(z1)) · (-z2) = SiLU(z1) · z2
```

这是实数代数等式；FP16 的 bias、投影、cast 和 activation 舍入顺序可能不同，因此不能据此声称逐位等价。完整调用链推导见[源码审计 §10.1](05_SwiGLU_TOP3_LOCAL_SUPPLEMENT_20261109.md#101-名次-2-的负形式-silu是有意的代数变换)。

case8 的 32+1 分段也是按定义将点积拆项：

```text
Σ(k=0..32) x[k]w[k] = Σ(k=0..31) x[k]w[k] + x[32]w[32]
```

它允许主段按 32 项向量化，并将尾项单独并入累加；但是否满足题目容差，还取决于规约树和舍入顺序，不能仅由代数恒等式推出数值等价。

### R：复用前提与边界

| 可迁移思路 | 使用前提 | 必须重做的部分 |
|---|---|---|
| 小 `M`/小 `d` 选择 AIV/vector 路径 | 实际工作量不足以摊薄 Cube/混合核开销，向量规约满足误差契约 | 目标芯片启动开销、输出量、掩码及归约顺序 |
| 合并共享输入的双投影 | 输入确可复用；两路权重布局能放入目标片上存储；消费者可识别合并后的结果 | N/K tiling、L0B/L0C占用、Fixpipe layout、同步 flag 和 workspace 生命周期 |
| 固定非对齐维的编译期 mask/pack | 维数/尾部固定；有效槽、越界地址、最终输出范围有证明 | mask 位、数据排列、尾块与输出压缩；不能复制本题偏移常量 |
| 双槽预取与 producer/consumer 重叠 | 确有可重叠阶段，槽位有明确 ready/reuse 协议 | event ID、交接时序、尾波与空波；不能照搬事件编号 |
| 编译期减少 tiling payload / 特化 key | Host 写入布局、TPL key、kernel entry ABI 成对一致 | 编译实例、结构对齐、所用 CANN 与编译器接口 |

本届固定评测平台是 CANN 9.0.0.0 / 910B4 / 20 AIC；下次赛事若平台或约束改变，所有硬件容量、并行度和 API 行为都需重新核对。不要把这条复用前提写成对本届成绩的额外防御条件。

## 5. 不显眼但不宜照搬的设计

1. **Rank2 的负形式 SiLU**：看起来像是多绕一步，实际是两路符号配对的数学实现。只有顺序和调用保持成对时才成立，孤立复制 `NegativeSilu` 会算错符号。
2. **Rank1 的 `PACKED_N`**：不是简单将 N 翻倍。需要修改权重打包、Mmad N、Fixpipe 和 AIV 读取布局；本题 d=256 且片上预算适配，不能外推到更大 N。
3. **Rank1 case8 的常量 mask**：省去动态索引生成，但仍需 GatherMask、pad/pack 和尾项逻辑。用不同 d 或行组时位模式会变，不能只拷贝常量。
4. **Rank3 的多 `TILING_KEY_VAR` 与自定义 wrapper**：用编译期隔离模板/tiling ABI，另有 workspace/runtime wrapper 适配代码。这是强环境绑定的工程技巧，不是通用优化；先确认 CANN 版本、入口 ABI、key 与构建包装器，不要照搬宏改写。
5. **Rank3 PATH51 行覆盖疑点**：静态枚举模板覆盖量大于题目 M，而现有审计未找到明确裁剪。报告将其记录为待解释风险，不据此断言获奖实现越界；任何迁移都应先完整证明最后 tile 的读写边界。

## 6. 后续比赛可复用的读码顺序

1. 先写题面运算、dtype/舍入和边界；将算法等式与实际浮点执行顺序分开。
2. 建 shape→Host条件→key→编译分区→入口→设备执行族表，先确认活跃代码。
3. 对大任务画共享输入、片上布局、workspace、producer/consumer 和 flag 生命周期；对小任务算清启动与搬运成本。
4. 将设计拆为 S（源码事实）、M（数学关系）、R（迁移前提）；某项性能收益只有在同一评测条件下比较后才作因果结论。
5. 新比赛移植时从一条可解释基线起步，一次只改一种数据布局/同步机制；正确性与速度分开记录。
